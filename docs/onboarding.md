# Pair an Echo and decide who can use it

## Start with guest access

Each household runs its own bridge and Alexa development skill. Register the Echo with the Amazon account authorized to test that skill. Start with [Home Assistant setup](home-assistant.md) so you can make the intended Echo speak a test sentence. Then use [Install the bridge](install.md) to set up HTTPS and connect your private Hermes Runs API.

1. **Pair the Echo.** Start the short capture described in the [device mapping instructions](install.md#4-map-one-echo-at-a-time-without-publishing-ids). On the intended Echo say, “Alexa, open Hermes Helper.” Listen for “Echo pairing recorded.” The person running the bridge then maps that captured device to the Home Assistant Speak entity they already tested. Repeat for each Echo. This step identifies the device and tells the bridge where to send the answer; it does not identify the speaker.
2. **Set up the guest profile.** Use a dedicated profile with only the `web` toolset and no personal connectors, memory, or files exposed to its tools. For a guest profile named `alexavoice`, use `hermes -p alexavoice config set platform_toolsets.api_server '["web"]'` in Bash. Verify the effective tools on the running guest API and try a live web lookup. A prompt or a different session key alone does not restrict tools. Without an `owner` block, the bridge keeps its existing single-profile behavior; anyone on a paired Echo can ask the configured profile to use its tools.
3. **Try a question.** Start the bridge and say, “Alexa, ask Hermes Helper to find out what two plus two is.” Expect “Working on it,” then a separate answer on that same Echo. An unmapped Echo cannot start a Hermes run, even if Alexa lets it invoke the development skill.

## Optional: automatically route recognized owners

1. Enable Alexa Voice ID and **Personalize skills** on the owner’s Alexa profile. This is separate from device pairing and from registering that Voice ID with the bridge.
2. Configure two separate private [Hermes API servers](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server), with different origins, backing profile data stores and `API_SERVER_KEY` values. Use [the split configuration example](../examples/bridge.owner.example.json): `hermes_origin` is **guest**; `owner.hermes_origin` is **owner**; `owner.fingerprint_file` points to a private file, relative to the config directory or absolute. Keep both APIs off the public proxy. Inject the guest key as `HERMES_ALEXA_HERMES_TOKEN`, the owner key as `HERMES_ALEXA_OWNER_TOKEN`, and the Home Assistant token as `HERMES_ALEXA_HA_TOKEN` via the private service environment. Keep config and identity files in a directory writable only by the operator/service (use `0700` directories and `0600` files on POSIX, restrictive ACLs on Windows).
3. Run `server.py check --config <private-config>` with the three keys available. This checks local configuration only. If you already have a fingerprint produced by the bridge enrollment helper, point to that file and use normal `serve`; **do not re-enroll**. A missing file means guest-only until registration; an existing malformed or unsafe file prevents startup.
4. To register for the first time, arm the bridge in a private interactive terminal using the venv Python. Use the private pair-capture JSON (`user_id` and `device_id`) for the intended Echo; that pair must already be in `routes_file`.

   ```text
   python -B server.py serve --config <private-config> --enroll-from <private-pair-capture>
   ```

   At the hidden prompt enter `register` followed by 5–12 randomly chosen lowercase words. Keep the phrase private and only arm enrollment while you control that Echo. Within **120 seconds**, use the normal question invocation and speak the exact phrase. “Voice ID recorded” means the fingerprint was saved and activated. The **next ordinary signed request** Alexa recognizes as that owner automatically uses the owner profile. No restart, config edit, second command, PIN or phone is needed after registration. Subsequent starts use normal `serve --config <private-config>` without `--enroll-from`.

Register once per skill and Alexa account, not per room; pair each additional Echo separately. A missing or unmatched Voice ID on a paired Echo uses guest. Owner and guest have separate history keys, queues, steering and retry state; an uncertain owner admission is not retried on guest. Enabling split routing starts fresh Alexa history keys for both profiles; old sessions are not migrated or deleted. Each reply goes only to the Echo that started its turn. A correction from another Echo does not move that reply. Alexa recognition is not strong authentication, and anyone within earshot can hear a delayed reply, even after the owner has left. Choose owner tool permissions and approval policies accordingly.

Before relying on it, confirm a harmless owner-only read on the registered Echo and another paired Echo; check that an unrecognized speaker can use web lookup but not owner tools; and check that an unmapped Echo cannot start a run. To turn off owner access, stop the bridge while idle, remove the `owner` block and owner key, keep `hermes_origin` pointed at the guest profile, and restart. This does not erase the fingerprint or old transcripts.
