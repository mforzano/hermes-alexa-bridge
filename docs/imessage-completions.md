# Owner Alexa background completion status in iMessage

This separate, opt-in relay sends a brief status such as **Alexa background work finished: 1 completed, 0 failed.** It does not speak an announcement, change ordinary Alexa replies, forward task text or attachments, or run an agent. It covers Hermes detached delegation delivery rows, not arbitrary background jobs, inline subagent results, or interim failure notices. The guest profile is not a source.

## Private setup (operator only)

1. Use the host running Hermes and Python 3.10 or later. The owner Voice ID lane must already be enabled. Verify the owner Runs endpoint’s effective profile, not merely its port or the current shell profile. The relay reads that profile’s `state.db`, not the guest store or an export. This metadata reader was validated on Hermes `ae2a81ccc0` (state schema 33); rerun the compatibility checks after upgrading Hermes, even when the schema number is unchanged.
2. In the Photon sending profile, run `hermes send --list photon --json`. Compare the exact native `id` against the origin metadata of the existing authorized iMessage DM **privately**. A listing alone does not prove the DM is yours; do not select by display name, sole result, or home channel. The route must be type `dm` with no thread and use the native `any;-;+…` ID. The running Hermes gateway must own that profile’s Photon sidecar. Use a native Hermes CLI executable that honors `HERMES_HOME`, not a shell alias or `.cmd` wrapper.
3. Copy [the example](../examples/completion.example.json) outside the checkout. Set absolute paths and the verified exact DM ID. Keep config and ledger in a directory writable only by the operator/task account. `source_home` is the owner Alexa profile; `photon_home` is the verified DM’s profile (they can be the same). Do not enter credentials; Hermes resolves its own Photon credentials. Set `owner_keys` to the exact keys emitted by the deployed bridge’s owner lane: `alexa:owner:household:voice:v1` for House and, if configured, `alexa:owner:echo:voice:v1:<digest>` for each per-Echo conversation. The digest is the bridge’s `Policy.conversation_for` SHA-256 of `json.dumps([skill_id, device_id])`; compute locally from approved private routes. Do not match a prefix in the database or substitute a session ID. Existing bindings are verified against both the API receipt and session origin; unbound configured keys remain idle until bound.
4. Run `python completion_bridge.py check --config <private-config>` from the intended task account and inspect the reported count. Confirm at least one session segment and the expected private source profile before proceeding. This checks existing metadata and route discovery without sending or writing state.
5. When ready to enable, run `python completion_bridge.py activate --config <private-config>` once. This snapshots the current committed message high-water mark and records already-known completion IDs without sending. Then enable the scheduled `poll` action. Do not reinitialize the ledger on routine restart.

## Scheduling and verification

On Windows, prefer **Task Scheduler** for this one-shot Python worker. It keeps execution independent of chat/model jobs and gives an observable exit code. Use the same non-elevated account as the Hermes gateway. Set the program to the absolute path of `python.exe`, arguments to `"<checkout>\\completion_bridge.py" poll --config "<private-config>"`, and **Start in** to the checkout. Repeat every minute, enable **Start the task as soon as possible after a scheduled start is missed**, choose **Do not start a new instance**, and set an execution limit of 15 minutes. Choose logon behavior appropriate for the existing gateway. Do not set automatic restart on failure. Verify the task’s Last Run Result and the relay’s `status` output. Hermes cron is also possible with a profile-local wrapper, `--no-agent --deliver local --failure-deliver local`, but adds a gateway scheduling/script dependency; cron must not deliver script stdout to Photon.

To confirm live behavior, the operator should arrange one harmless owner Alexa delegation after activation, let the ordinary reply finish, and verify one status in the exact DM without another Alexa question or Echo announcement. Check the ledger with `python completion_bridge.py status --config <private-config>`; `accepted` means Photon supplied a message ID, not that the phone displayed it. `poll` exits 0 for no failures, 1 for a local/setup error, and 2 when it records a rejected or ambiguous attempt. The ledger stores hashed completion IDs, row IDs and outcome labels, not task text.

A definite rejection and an ambiguous acceptance are recorded separately. **Neither is retried by this relay.** A killed process can leave a claim ambiguous even if nothing was sent. Reconcile against the existing DM before taking any manual action. Keep the ledger on a local disk; do not restore an old ledger against a newer source DB. A source file replacement, source sequence regression, or route/key change must be reviewed with the schedule disabled. If intentionally changing scope, activate a new private ledger at the new cutover; it starts from that point, not the old backlog. Disable the task to stop forwarding; ordinary Alexa replies are independent.

## Compatibility boundary

The HTTP history projection omits the detached unit ID and is not an authorization boundary. The relay uses a read-only SQLite snapshot of the profile-local declared-key registry, corresponding API binding receipt, session origin and display metadata. Compression edges must retain the same API route and origin, exclude reset/branch/delegate markers and independent bindings, and be unambiguous. Polling uses SQLite’s `messages` AUTOINCREMENT sequence and a separate claim ledger. The relay never selects `messages.content` or interprets completion text. Delivery depends on Hermes successfully persisting the detached row; deleting/pruning it before the next poll can make a notice unavailable.
