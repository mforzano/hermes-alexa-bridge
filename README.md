# Hermes Alexa Bridge

A local prototype for using stock Echos with Hermes. House is the shared default; an operator can give each Echo its own conversation. Alexa acknowledges receipt and ends the skill session without waiting for Hermes or Home Assistant. While a conversation is active, another invocation in that conversation can steer its existing run. The final answer goes **only to the Echo that started that run**.

## Run locally

From the project root, with Python 3.10+ (tested on Windows with 3.14):

```sh
python -B -m unittest discover -v
python -B demo.py
```

No pip packages, logins, tokens, or VM required. `demo.py` sends three synthetic Alexa requests (two on the same simulated Echo in separate Alexa sessions, one on a different Echo) through the real bridge and local HTTP clients. It prints acknowledgments in milliseconds, the shared Hermes key, and the exact recipient and message of each simulated notification. The two ephemeral HTTP listeners bind to `127.0.0.1` only and close after the run. The Alexa verifier in the demo is a fixture, **not** Alexa authentication; no Alexa listener is started. Synthetic conversation continuity is not proof of persistence on a real Hermes host.

## How it works

- `ingress.py`: raw-body verification seam plus Alexa reply formatting. The optional `alexa_sdk_verifier()` adapter delegates cryptographic verification to Amazon’s ASK SDK. It requires an independently provisioned HTTP ingress and has not been exercised with a live SDK or signed Alexa request.
- `bridge.py`: exact skill ID and `(user ID, device ID)` allowlist, signed timestamp freshness ±150 seconds, bounded in-memory scheduling, and request-ID deduplication for at least 305 seconds. Resolve the configured conversation before looking for an active run. No broadcast or Alexa-session-based routing.
- `clients.py`: create a run with `POST /v1/runs`, `X-Hermes-Session-Key`, and a request-scoped `Idempotency-Key`; poll `GET /v1/runs/{run_id}`. A follow-up targets that run with `POST /v1/runs/{run_id}/steer` and `{"input":"…"}`. An accepted steer is queued for the next tool boundary, not an interruption or proof that the model read it. The bridge reads terminal `pending_steer` from status, or checks the matching terminal SSE event when canonical status omits the field. Only complete runs speak, using `POST /api/services/notify/send_message` to one HA Speak entity, with plain text capped at 600 characters. HA's success means service accepted, not that sound was heard.
- A request received while a run ID is still being obtained can queue as an ordinary follow-up. A refused steer is never promoted to a new turn: a later terminal status does not prove that the refusal was a harmless completion race. The bridge replays an accepted or uncertain steer only if trustworthy terminal `pending_steer` maps unambiguously to the original request and no pause or stop was observed (including canonical `pending_controls`). Each replay uses the original request’s Echo and idempotency key. Alexa acknowledges receipt, not upstream acceptance or playback. If a correction gets no reply, wait until the conversation is idle and ask again explicitly if it is still needed; an unconfirmed steer may already have been applied.
- Defaults: four outstanding requests (including steers awaiting disposition), 256 dedup records, 120-second queue age, 250 ms poll interval, 10-minute run observation budget, 32 KiB Alexa body and 1 MiB Hermes read limits. One background worker serializes HTTP calls across conversations; a slow upstream can delay controls, not Alexa acknowledgments. Socket timeouts (Hermes 75 s; terminal event lookup at most 5 s per socket operation; HA 10 s) are **not** absolute deadlines. If a create fails without a usable run ID, or run observation times out, the bridge blocks that history for the life of the process. Already queued requests for it are dropped without speech and later requests report busy; other histories can continue. Do not restart to clear the block until you have verified that the earlier create did not start a run or that the run has ended. The bridge does not resolve Hermes `unknown` runs, answer approvals, or retry HA speech. Failure and ambiguity produce counters rather than audible diagnostics. Queue, run ownership, and dedup state are volatile; use one bridge instance per voice profile and do not assume crash-proof delivery.

### Default conversation configuration

Construct `Policy.from_config(json.load(...))` from a protected operator-owned file shaped like [`examples/routes.example.json`](examples/routes.example.json), then pass that policy and the `Hermes` client to `Bridge(policy, hermes, ha.speak)`. Set `default_conversation` to `house` (or omit it) or `echo`. If several allowed users map to the same Echo, all of those rows must agree. House retains `alexa:household:voice:v1`; Echo-only keys use a separate namespace and a stable hash of the configured skill and device IDs, not the HA entity, display name, speaker, or Alexa session ID. A default change selects a different history on future requests; it does not move or delete anything. Drain the bridge before applying a new policy. There is no dashboard, hot reload, voice override, or speaker authentication.

## Integration handoff — not provisioned by this project

1. **Alexa custom skill.** In the Alexa developer console, create a development Custom skill using the Echo’s locale. Start with [`examples/interaction-model.en-US.json`](examples/interaction-model.en-US.json) for en-US. Enable development testing with an authorized account on one stock Echo and try “Alexa, ask Hermes Helper to find out [question].” `AMAZON.SearchQuery` captures the question after a carrier phrase, not arbitrary always-listening speech. Validate invocation and slot transcription before adding other Dots. No public skill publication is required for same-account development testing; public source release does not publish the skill.
2. **Trusted ingress.** The HTTPS option is an Alexa-reachable, dedicated TLS endpoint accepting only the skill POST. Use an isolated reverse proxy/application adapter with the official `ask-sdk-webservice-support` package, pinned and reviewed before use. Instantiate `alexa_sdk_verifier()` once, enforce body size before buffering, reject duplicates of `Signature-256` or `SignatureCertChainUrl` case-insensitively, and preserve both headers and the exact raw body bytes. Then call `handle_alexa(headers, raw_bytes, verifier, bridge.submit_verified)`. Return its status and JSON directly. The SDK checks the signature and certificate; the bridge checks the signed request timestamp and skill/user/device IDs. Configure bounded concurrency and a total ingress deadline comfortably under Alexa’s approximately eight seconds, including certificate fetch/cold start; measure this on a real device. Do not pass an always-true verifier or expose a `submit_verified` route. Keep Hermes and HA unreachable from the public internet. If the verifier and worker run separately, use a separately authenticated private transport that only the verified ingress can write to, with bounded admission and no public bypass. **Alternative design, not implemented:** Alexa Skills Kit → AWS Lambda trigger restricted to the exact skill ID, with no Function URL or other untrusted invokers → authenticated private relay/queue with an always-on LAN consumer. A Lambda process-local worker is not a delivery mechanism after Lambda returns.
3. **Hermes.** Enable the private, authenticated API Server and check `GET /v1/capabilities` for run creation/status/steer, SSE replay, and `X-Hermes-Session-Key`. The contract was source-checked against Hermes Agent **v0.23.2, revision `ae2a81ccc00e`**; no release is live-certified here and Responses-only builds are unsupported. Capabilities alone are insufficient: verify Runs history actually continues with the declared key and the installed mode exposes terminal `pending_steer` in status or the terminal event. The inspected canonical projection omits it from GET, so this bridge looks for the terminal event; if that event is missing, expired, mismatched, or the server cannot preserve exact steer text, no fallback is guessed. There is no downgrade to a second Responses turn. Use loopback or trusted private HTTPS and a bearer key from protected secret storage. Never bind a private messaging history to the voice profile. Separate voice transcripts are not security boundaries: people nearby can speak and listen, and memory/connectors/tools may still be shared. Verify effective least privilege before connecting real devices.
4. **Home Assistant VM.** Start the existing VM only when authorized. Confirm Core 2025.6 or newer with the **Alexa Devices** integration; choose a currently supported Core release. In **Settings → Devices & services**, add Alexa Devices using the authorized Amazon account and app-based MFA as required by HA. Check each physical Dot has its own enabled Speak notify entity. Use **Developer tools → Actions** to run `notify.send_message` against exactly one Speak entity with harmless text, and listen in that room. Supply the bridge with a dedicated, least-privilege confirmed-working HA REST bearer credential. HA tokens inherit user permissions and are not automatically limited to this one service. From the bridge host use private trusted HTTPS to HA (LAN, private VPN, or TLS reverse proxy on the private network); the client's HTTP exception is literal loopback only. Do not use public port forwarding, certificate bypass, `alexa_media`, Announce groups, or HA `/api/states` to deliver speech.
5. **Private configuration and acceptance.** Pair each verified Alexa device ID with its independently tested HA Speak entity; obtain IDs only from verified requests in a narrow provisioning flow, and disable payload logging. Verify shared recall across Alexa sessions and Dots, correction mid-tool and after the last tool boundary, speech on the initiating Dot only, fallback speech on its own Dot, no automatic replay after a refused steer, and no crossover with Echo-only history. Restart while idle and test recall. Verify unmapped requests, duplicate requests, and HA failure. Add rate controls and redacted monitoring before a pilot. To disable, remove the skill trigger, stop the bridge, revoke its credentials, and disable ingress without deleting transcripts.
